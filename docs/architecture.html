01 · Capabilities

Features and the logic behind them

Lumen is a multi-user blog: anyone can read, signed-in users write, like and comment, and admins moderate. Each feature below lists what the user sees and how it works underneath.

F1

Reading and discovery

What users get

  • A home feed of published posts, newest first, with a hero, trending posts and a topics sidebar.
  • Post pages, author profiles (/u/:username) and topic pages (/t/:slug).
  • 14 curated topics, from AI and Web Development to Travel and Personal Finance.

How it works

  • The feed is GET /posts, paginated (default 20 per page, max 100), ordered by published_at desc, id. The id tie-breaker keeps pages stable.
  • Only posts with status = published and no deleted_at are visible to readers.
  • Like and comment counts are computed in the same SQL query as subqueries, so the list never makes one extra query per post.
  • TanStack Query caches each page in the browser, so going back to the feed is instant.
F2

Search

What users get

  • A search box that understands phrases ("rich text"), OR, and exclusions (-draft), like a web search engine.
  • Results can be narrowed by author and topic.

How it works

  • PostgreSQL full-text search. Each post has a stored search_vector column that the database computes itself from the title and content. Title words are weighted higher than body words.
  • A GIN index on that column makes search fast without scanning every post.
  • The query is parsed by websearch_to_tsquery('english'), which also handles stemming, so “writing” matches “write”.
  • Results are sorted by ts_rank (relevance), then newest first.
F3

Trending posts

7-day window

What users get

  • A “Trending” list of 5 posts on the home page: the posts people are reacting to right now, not just the most popular of all time.

Why this design

  • Counting only recent activity lets a new post with a burst of likes beat an old post that has many likes but no new ones.
  • The all-time tie-breakers make sure the list is never empty or random on a quiet week.

Ranking logic · PostRepository.trending

since = now − 7 days score = likes since + comments since (deleted comments don't count) ORDER BY score DESC, like_count + comment_count DESC, published_at DESC, id

Only published, non-deleted posts. GET /posts/trending?limit=5 (1 to 20).

Example postLikes (7 d)Comments (7 d)ScoreAll-timeRank
New post, published 2 days ago9413131
Classic guide from last year3142102

Illustrative numbers. The classic guide and last month's post tie on a score of 4, so the all-time total decides the order.

F4

Trending topics

7-day window

What users get

  • The sidebar shows 3 “Trending topics” at the top, then the rest of the topics.
  • Clicking a topic opens its page with all of its posts.

Why this design

  • A topic is trending when its posts are getting attention, so it reuses the same engagement signal as trending posts.
  • A post can have up to 3 topics, so one popular post lifts each of its topics.

Ranking logic · TopicRepository.trending

for each topic: engagement = likes + comments in the last 7 days on its posts published = its published posts ORDER BY engagement DESC, published DESC, position ASC -- curated

GET /topics/trending?limit=3. The browser caches the answer for 5 minutes (staleTime), so the sidebar doesn't re-query on every page.

F5

Writing and publishing

What users get

  • A rich-text editor (Tiptap): headings, bold, italic, lists, quotes, code, tables, links, colours, fonts and alignment.
  • Drafts, publish and unpublish, cover images, up to 3 topics, and an unsaved-changes warning (⌘S saves).
  • “My posts” and “Drafts” pages.

How it works

  • Safe HTML, twice. The editor produces HTML. The server cleans it with nh3 using an allowlist of tags and styles before saving, and the browser cleans it again with DOMPurify before showing it. A script can't get through either one.
  • Slugs. The URL slug follows the title while the post is a draft and is frozen once published, so shared links never break.
  • Excerpts are generated from the content unless the author writes one.
  • Covers are checked by their real file bytes (JPEG, PNG or WebP, max 5 MB) and saved with a random filename.
  • Older posts written in Markdown are still shown correctly (content_format).
F6

Check your writing

AI

A strip under the editor toolbar with three checks. Each opens a popup, and every accepted fix is a normal editor edit: it appears in the post at once, can be undone with ⌘Z, and is saved with the post. The server never stores the text it checks.

Grammar · LanguageTool + AI

  • The server sends the text to LanguageTool (word-level spelling, grammar, punctuation and style) and the AI (whole-sentence fixes) at the same time with asyncio.gather.
  • An AI fix is kept only if its original sentence really appears in the post, up to 40 fixes. That filters out made-up text.
  • Word issues inside a sentence the AI rewrote are hidden, so the writer isn't asked to fix the same thing twice.
  • If one source fails, the other's results still show, with a note.

Readability · in the browser

  • Calculated locally as the writer types, with no server call.
  • Flesch reading ease:
206.835 − 1.015 × words/sentence − 84.6 × syllables/word
  • 70+ easy · 60 fairly easy · 50 medium · below 50 hard.
  • Reading time at 200 words a minute. Sentences over 25 words are listed, each with Simplify with AI.

Tone · AI

  • The writer picks a target: professional, friendly, confident or casual.
  • The AI answers in JSON: the tone it hears, a one-line explanation, and up to 15 rewrites (original → fix, reason).
  • As with grammar, only rewrites whose original text is found in the post are shown.

AI provider chain · app/integrations/llm.py

DisabledThe editor says “AI checks aren't set up yet”; grammar still works through LanguageTool
  • Both providers use the same OpenAI-style /chat/completions call, in JSON mode at temperature 0.2. That's why one ChatModel class serves both.
  • If the first model returns 404 (retired), 429 (out of quota) or a 5xx (overloaded), the fallback model is tried. A 401 or 403 (bad key) stops at once, because the second model would fail the same way.
  • Prompt-injection guard. The post is wrapped in tags, and the model is told to treat it as text only and never follow instructions inside it.
  • Limits. Login required, 10 checks a minute per user, and at most 20,000 characters per check.
F7

Likes and comments

What users get

  • Like a post with one click. The heart fills at once, before the server answers.
  • Comment threads under each post. Authors delete their own comments; admins can delete any.

How it works

  • Likes are PUT / DELETE /posts/{id}/like. The primary key (user_id, post_id) makes a double like impossible, and repeating the request is harmless. You can't like your own post.
  • The UI is optimistic: it updates the cache first and rolls back if the request fails.
  • Moderation. Every comment is checked before it's saved: by a word list by default, or by an external moderation API when one is set up. A rejected comment gets a 422 content_rejected. If the moderation API is down, the comment is accepted and a warning is logged, so the site keeps working.
  • 10 comments a minute per user.
F8

Admin and audit log

What users get

  • An admin area to list users and change their roles.
  • An audit log page showing who did what, and when.
  • Admins can edit, unpublish or delete any post and delete any comment.

How it works

  • Role-based access: every protected route declares a permission (require_permission). The role is read from the database on every request, so a demotion works at once, even with a valid token.
  • Recorded actions: user.role_changed, post.updated, post.published, post.unpublished, post.deleted and comment.deleted.
  • Each audit row is written in the same transaction as the change, so there's never a change without a record, or a record without a change. The log is append-only.
F9

Export your posts

What users get

  • Download all your posts, drafts included, as lumen-posts-YYYY-MM-DD.csv, optionally filtered by status.

How it works

  • Streamed: rows are read from the database 500 at a time and sent as they're ready, so a large export never has to fit in memory.
  • Cells that start with =, +, -, @ or a tab are escaped, so a spreadsheet can't run them as formulas. A UTF-8 BOM makes Excel show accents correctly.
F10

Themes and phones

  • Light, dark and “system” themes, remembered per browser.
  • Layouts for phones: the sidebar stacks and the check popups become bottom sheets.

How it works

  • All colours are CSS variables. useTheme sets data-theme on the page, and “system” follows the operating system's prefers-color-scheme.

02 · The whole system

System architecture

Three tiers: a React single-page app in the browser, a stateless FastAPI service, and PostgreSQL. The API and database run as Docker Compose containers. The API is the only part that talks to the database or to outside services.

Reading the diagram. The browser never talks to the database or to the AI. Every request goes to the API, which checks who you are, applies the rules, reads or writes Postgres, and calls outside services only for writing checks and optional moderation. That's what keeps the API key and the database password on the server.

The API is stateless: logins are signed tokens, not server sessions, so more API containers could run behind a load balancer without changes. Rate-limit counters are the one exception (they live in memory; see section 07).

03 · Frontend

The logic behind it

  • Server state is not app state. Posts, topics and comments belong to the server, so TanStack Query owns them. There's no Redux: the only real client state is the login token and the theme, each kept in a small context.
  • One client, one error shape. Every failure becomes an ApiError, so every screen shows errors the same way, including the request id to search for in the logs.
  • Applying fixes safely. LanguageTool and the AI return positions in plain text, but the editor holds a formatted document. lib/editorText.ts builds the plain text and a map from each character back to its position in the document, re-finds the original words before replacing them, and keeps bold, colours and links intact.

Rendering a post safely

  • PostBody checks content_format. HTML goes through DOMPurify with the same allowlist the server uses; Markdown (older posts) goes through the Markdown renderer.
  • The server is the real safety line (nh3). The browser pass is a second line in case bad HTML was ever stored.
  • Cover images load from /uploads, which the proxy sends to the API.

The logic behind it

  • Thin routes, testable rules. A route only parses input, runs its dependencies and calls a service. The rules live in services, where they're easy to test.
  • Dependency injection. Login, permissions and rate limits are FastAPI dependencies, so a route shows at a glance what it requires, and tests can replace them.
  • Interfaces for the outside world. Services depend on GrammarChecker, LanguageModel, Moderator and Storage protocols. The real classes are built once at startup, and tests use fakes, so the 263 tests never call the internet.
  • Async all the way. The database driver (asyncpg) and the HTTP clients (httpx2) are async, and grammar runs LanguageTool and the AI in parallel on one worker.

The logic behind it

  • Computed, not duplicated. like_count and comment_count are subqueries that run with the query, not stored columns. They can never drift out of sync, and trending needs the timestamped rows anyway.
  • A search vector the database keeps up to date. search_vector is a generated, stored column. Postgres rebuilds it whenever the title or content changes, so application code can't forget to.
  • Soft deletes for posts and comments (deleted_at). Deleted content disappears everywhere but stays recoverable, and audit entries still point to something.
  • Composite primary keys on likes and post_topics enforce the rules (“one like per person”) in the database itself.

Migrations and data

  • Every schema change is an Alembic migration. The API container runs alembic upgrade head on start, and CI runs alembic check to catch model changes that have no migration.
  • The 14 topics are added by a migration, so every environment has the same list.
  • python -m app.seed adds 10 sample authors and 35 posts, with likes and comments.
  • Tests run against a separate test database, never the dev data.
  • Cover images live in a separate uploads volume. The database stores only their path.

The trending query in SQL (simplified)

SELECT p.*
FROM posts p
WHERE p.status = 'published' AND p.deleted_at IS NULL
ORDER BY
  (SELECT count(*) FROM likes l    WHERE l.post_id = p.id AND l.created_at >= :since)
+ (SELECT count(*) FROM comments c WHERE c.post_id = p.id AND c.created_at >= :since
                                    AND c.deleted_at IS NULL)  DESC,
  p.like_count + p.comment_count  DESC,   -- all-time tie-breaker
  p.published_at DESC, p.id
LIMIT :limit;                              -- :since = now() - 7 days

06 · Interactions

How the parts work together

Four common journeys, step by step. The coloured label shows where each step runs.

A. Logging in and making a request

Browser

The login form sends POST /auth/login with the email or username and the password.

API · deps

limit_login_attempts allows 5 tries a minute per IP address and username.

Postgres

The user is looked up (username is case-insensitive).

API · core

Argon2 checks the password, then a JWT (HS256, valid 30 minutes) is signed with the user id.

Browser

client.ts saves the token in localStorage and adds Authorization: Bearer … to later calls.

API · deps

On every protected call, CurrentUser checks the token, loads the user and their current role, and require_permission allows or rejects the request with 403.

B. Publishing a post

Browser

The writer saves the draft: POST /posts (then PATCH) with the editor's HTML, title and topics.

API · service

The HTML is cleaned with nh3, the slug is built from the title (unique), the excerpt is generated, and topics are checked (at most 3, all real).

Postgres

The post and its post_topics rows are saved, and search_vector is generated automatically.

Browser

The writer clicks Publish: POST /posts/{id}/publish.

API · service

Checks ownership (or admin), sets status=published and published_at, freezes the slug, and writes the audit entry post.published, all in one transaction.

Browser

TanStack Query marks the post lists as stale, so the feed, profile and topic pages show the new post.

C. A grammar check

Browser

editorText.readDoc turns the document into plain text and sends POST /writing/grammar.

API · deps

Login required, limit_writing (10 a minute), and the text must be at most 20,000 characters.

External

LanguageTool and the AI (Gemini, falling back as needed) are called in parallel.

API · service

Word issues are mapped to categories. AI sentence fixes are kept only if their original text is found in the post (up to 40). If one source failed, a note is added.

Browser

Cards are grouped and overlapping word issues are hidden. Accept runs replaceTarget, which finds the words again and edits the document while keeping its formatting. It can be undone.

D. Loading the home page

Browser

HomePage and Layout start three queries in parallel: the feed, /posts/trending?limit=5 and /topics/trending?limit=3, plus /topics.

API · repo

The feed uses the status, published_at index. Trending runs the ranking queries with since = now − 7 days.

Postgres

Counts come from subqueries; nothing is precomputed or cached on the server.

API · middleware

Large JSON answers are gzipped, and every response carries its request id.

Browser

Results are cached: topic lists for 5 minutes, so moving between pages doesn't reload the sidebar.

A sliding window kept in memory (a deque of timestamps per key, cleaned up every 1,000 calls). It's simple and fast for one API container. With several containers it would move to Redis.

Protecting data

  • Argon2 password hashing
  • Short-lived JWTs, with the role re-checked from the database on every request
  • HTML allowlists on the server (nh3) and in the browser (DOMPurify)
  • Upload checks on the real file bytes, with random filenames
  • Formula-safe CSV export
  • Secrets only in .env, which git ignores

Failing gracefully

  • One error shape: {error: {code, message, request_id}}
  • Timeouts and retries on every outside call
  • AI fallback model when the first is busy or out of quota
  • Moderation API down → the comment is accepted and a warning logged
  • Grammar still works if the AI is down, and the reverse

Running it

  • structlog JSON logs with a request id on every line
  • /health (the process is up) and /ready (the database answers), used by the Docker healthcheck
  • Migrations run automatically on start
  • CI checks lint, format, migrations, tests, types and both builds on every change

08 · Why it's built this way

Key decisions

DecisionWhyTrade-off
A single-page app plus a JSON APIA clean split: the API could also serve a mobile app, and each side is tested on its ownNeeds client-side routing and no server rendering (less SEO out of the box)
Postgres full-text searchNo extra search server to run; the index stays up to date by itselfFewer features than Elasticsearch (no typo tolerance)
Trending computed live over 7 daysAlways correct, nothing to schedule, easy to explainAt large scale it would move to a cached or precomputed score
Stateless JWT, role read from the databaseNo session store; demotions work at onceOne user lookup per request (by primary key, so fast)
Rich text stored as cleaned HTMLWhat you see in the editor is what readers getIt needs an allowlist on both sides
AI behind a LanguageModel interfaceSwap Gemini or Groq by setting a key; tests use a fakeOnly features that work with any chat model can be used
Readability worked out in the browserInstant, free and private; it works without AIThe syllable count is a heuristic for English
An audit entry in the same transactionThe log can never disagree with the dataEvery admin write is slightly larger
Rate limits in memoryNo Redis needed for one containerCounters reset on restart and aren't shared between containers
